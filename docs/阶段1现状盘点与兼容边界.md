# 阶段 1 现状盘点与兼容边界

> 盘点日期：2026-07-27  
> 盘点范围：真实 MySQL 元数据、后端发布/编辑/审核/详情链路、前端对应页面、H2 测试结构、RAG 与周边业务依赖  
> 当前状态：现状盘点完成；尚未创建新表、修改生产表或编写迁移

## 1. 结论

当前系统已经具备房源创建、编辑、审核、公开展示、删除、发布付费、单图上传和通知链路，但房源模型只能表达基础价格、面积、户型、区域和自由描述，无法可靠表达通勤、楼层、电梯、费用、租期、朝向、家具家电明细及其来源与验证状态。

阶段 1 不能只向 `house` 表堆字段。后续方案必须同时满足：

1. 高频单值事实可直接过滤、排序和校验；
2. 家电、设施、媒体等重复项可以保存明细；
3. 旧接口和旧页面在过渡期继续读取；
4. 房东编辑后重新审核、发布付费、通知和 OSS 清理语义不变；
5. 真实 MySQL、Java 类型和 H2 测试结构恢复一致；
6. 历史数据不能从模糊描述中伪造确定事实；
7. 新模型能成为后续 Chroma/Elasticsearch、通勤服务和发布 Agent 的统一事实来源。

## 2. 数据库现状

### 2.1 迁移机制

- `pom.xml` 已引入 Flyway 和 MySQL Flyway 依赖。
- `application.yml` 中 `spring.flyway.enabled=false`，应用不会迁移真实 MySQL。
- 项目不存在生产迁移脚本目录，只有 H2 测试使用的 `src/test/resources/schema.sql`。
- 真实表的约束名和字段形态显示其来自原 Django 数据库结构。
- 在设计任何新表前，必须先明确数据库结构的唯一迁移所有者：Java/Flyway、Django，或人工发布脚本三者只能选一个主路径。

### 2.2 真实 `house` 表

真实表共有 153 条记录，当前字段为：

| 分类 | 字段 |
| --- | --- |
| 展示 | `id`、`title`、`description`、`image` |
| 租赁 | `price`、`house_type` |
| 户型 | `area`、`rooms`、`bedroom_count`、`living_room_count`、`bathroom_count`、`kitchen_count` |
| 地址 | `region_id`、`address_detail` |
| 生命周期 | `landlord_id`、`status`、`is_active`、`create_time`、`update_time` |
| 统计 | `click_count` |

表中只有主键、房东/区域外键及四个户型数量单列索引。缺少公开查询常用的组合索引、业务状态约束、价格/面积范围约束、版本字段和首次发布时间。

### 2.3 历史数据质量

| 检查项 | 结果 | 影响 |
| --- | ---: | --- |
| 总房源 | 153 | 全部为虚构数据 |
| 已审核且有效 | 110 | 当前公开检索和向量索引范围 |
| 已下架但 `is_active=1` | 43 | 状态字段与启用字段存在重复语义 |
| `bathroom_count` 为空 | 127 | 公开房源中 84 条为空 |
| `kitchen_count` 为空 | 135 | 公开房源中 92 条为空 |
| 关联街道 | 133 | 公开房源中 90 条 |
| 只关联顶级区域 | 20 | 公开房源中 20 条，缺少区县和街道 |
| 不同描述 | 62 | 153 条房源中 102 条位于重复描述组 |
| 不同图片 URL | 26 | 单图重复明显 |
| 提及地铁/轻轨 | 36 | 没有站点、线路和步行距离结构 |
| 提及“家电齐全” | 15 | 没有任何具体家电明细 |
| 提及具体家电名称 | 0 | 不能可靠回填家电清单 |
| 提及电梯 | 12 | 没有可验证的布尔字段 |

因此历史回填只能做以下两类操作：

- 可以确定的兼容复制，例如 `price -> rent_amount`、`area -> 面积字段`、`house_type -> 租赁方式`；
- 无法确定的字段保留 `NULL/UNKNOWN` 并降低完整度，不能把“家电齐全”“近地铁”等描述自动转换为已确认事实。

## 3. 已发现的结构契约不一致

### 3.1 地区层级类型不一致

真实 `area.level` 是 `VARCHAR(20)`，取值为：

- `province`：7 条；
- `district`：21 条；
- `street`：47 条。

但当前 Java `Area`、`AreaMapper`、`AreaController`、`AreaView` 和 H2 `schema.sql` 使用整数；前端发布/编辑页传递 `1/2/3`。

真实运行验证结果：

- `GET /api/areas/?level=1` 返回空数组；
- `GET /api/areas/` 因字符串无法映射为 `Integer` 返回 HTTP 500。

这会直接阻断传统发布和编辑页面的三级地区选择。阶段 1 必须先统一该契约，且不能继续让 H2 测试结构掩盖真实库问题。

### 3.2 房源删除规则不一致

真实库中 `favorite`、`browse_history`、`chat_room`、`message`、`point_purchase_record`、`publish_record` 和 `recommend_point` 对 `house` 的外键删除规则均为 `NO ACTION`。

H2 测试结构则混用 `ON DELETE CASCADE` 和 `ON DELETE SET NULL`，而 `HouseService.delete` 直接物理删除 `house`。真实库目前已有收藏、浏览、通知、发布付费和推荐点引用，因此部分房源的删除接口可能在生产 MySQL 上失败，但测试仍会通过。

阶段 1 必须确定房源删除策略：业务软删除、统一调整外键规则，或显式清理依赖；不能保持当前不一致。

### 3.3 其他一致性问题

- 真实 `description` 为 `LONGTEXT`，测试表为 `TEXT`。
- 真实 `area.level` 为字符串，测试表为整数。
- 真实外键删除规则与测试表不同。
- `status='offline'` 的 43 条记录仍为 `is_active=1`，当前公开查询依赖两个条件共同判断。
- DTO 中 `rooms` 可提交，但服务端始终根据四个户型数量重新生成，属于兼容展示字段而非事实来源。

## 4. 后端业务链路

### 4.1 发布

`POST /api/houses/` 的现有流程：

1. 从 JWT 注入用户编号；
2. 校验用户角色为 `landlord` 或 `admin`；
3. 检查三次免费额度，必要时锁定一条未使用的付费记录；
4. 合并请求字段并执行服务端验证；
5. 写入 `status=pending`、`is_active=true` 的房源；
6. 将付费记录绑定到房源；
7. 发送新房源审核通知。

整个流程处于同一事务中。新模型必须继续保证发布资格、主表、明细表和通知之间的原子性。

### 4.2 编辑

`PUT/PATCH /api/houses/{id}/` 支持房东和管理员：

- 房东只能编辑自己的房源；
- 普通房东修改后房源重新进入 `pending`；
- 管理员修改时保留原审核状态；
- 封面地址变化后，在事务提交后删除旧 OSS 对象；
- PUT 和 PATCH 当前实际共用同一套“未提供字段保持原值”语义。

新字段和子表更新必须支持局部修改、并发版本检查和重新审核，不能用“整表先删后插”造成未修改信息丢失。

### 4.3 审核

管理端支持：

- `approve`：状态改为 `approved`；
- `reject`：状态改为 `rejected`，退还对应发布付费记录；
- `offline`：状态改为 `offline` 且 `is_active=false`；
- 每个动作都会发送通知。

当前没有审核原因、字段冲突、审核版本、审核记录或索引同步状态。阶段 1 的表设计至少要为这些后续能力保留明确边界。

### 4.4 详情与隐私

公开房源详情会隐藏精确地址和房东手机号；管理员和所属房东可以读取。非公开房源对其他用户统一返回 404，避免泄露存在性。新增坐标、门牌、权属证据等字段必须沿用或强化这一权限边界。

### 4.5 现有接口契约

| 接口 | 现有用途 | 兼容要求 |
| --- | --- | --- |
| `GET /api/houses/` | 公开列表与基础筛选 | 旧查询参数继续可用 |
| `GET /api/houses/{id}/` | 公开/私有详情 | 旧响应字段继续保留 |
| `GET /api/houses/my/` | 房东房源列表 | 状态与分页语义不变 |
| `POST /api/houses/` | 创建并进入审核 | 旧请求在过渡期可转换 |
| `PUT/PATCH /api/houses/{id}/` | 编辑并可能重审 | 必须支持新旧字段并发过渡 |
| `DELETE /api/houses/{id}/` | 当前为物理删除 | 删除策略必须重新确定 |
| `PUT /api/admin/houses/{id}/audit/` | 审核/拒绝/下架 | 付费和通知事务不能丢失 |
| `POST/DELETE /api/upload/` | 单图 OSS 上传/删除 | 多图后仍需保留安全归属检查 |

## 5. 前端现状

### 5.1 发布与编辑

当前两个页面分别实现了高度重复的表单逻辑，只支持：

- 标题、自由描述；
- 室/厅/卫/厨；
- 整租/合租；
- 月租、整数面积；
- 三级地区和详细地址；
- 一张封面图。

当前缺少草稿自动保存、多图、家电清单、费用、楼层、电梯、朝向、租期、起租时间、宠物规则、字段未知态、预览和完整度提示。发布和编辑应在阶段 1 复用同一套表单分区及校验模型，避免继续维护两份字段逻辑。

### 5.2 详情页

详情页只展示封面、标题、租金、户型、面积、租赁方式、区域、地址、自由描述和房东信息。后续需要按基本信息、费用、配置、租赁条件、媒体和验证信息分区，但公开访问仍需隐藏精确位置。

### 5.3 管理审核

管理端列表只支持标题与状态筛选；详情弹窗只能查看现有基础字段，审核动作没有原因输入。新模型上线前，审核页必须能查看新增事实、未知项、来源和冲突，否则详细数据只在发布端存在，无法形成质量闭环。

### 5.4 自动化测试

- 后端已有房源生命周期、权限、管理审核、发布付费和上传边界集成测试。
- 前端没有发现业务页面单元测试或端到端测试。
- 现有 H2 结构与真实 MySQL 不一致，新增迁移测试前必须先消除结构漂移。

## 6. 检索与周边依赖

房源字段被以下模块直接消费：

- 普通列表筛选与详情；
- AI MySQL 硬过滤和房源候选卡片；
- Chroma 房源文档构建与索引健康水位；
- 相似房源和个性化推荐；
- 收藏、浏览历史、聊天房源卡片和站内通知；
- 发布额度、付费记录、推荐点和点击统计；
- 管理看板的状态、类型、价格、面积和区域统计。

因此阶段 1 需要兼容读模型，而不是只改 `HouseUpsertRequest`。详细字段完成后必须重建 Chroma 文档和阶段 1 评测集；阶段 2 切换 Elasticsearch 后再次校准。

## 7. 新数据库设计必须满足的边界

下面是进入新表设计前已经确定的约束，不代表最终表结构：

1. `house.id`、房东关联、审核状态和现有业务外键必须保持稳定。
2. 价格、面积、户型等旧字段不能一次性删除或改名；需要兼容窗口。
3. 单值、高频过滤字段不能只放 JSON 或自由描述。
4. 家电、设施和媒体不能继续压成布尔值或逗号字符串。
5. `NULL/UNKNOWN` 必须与 `false/0` 区分。
6. 字段来源与验证状态必须能表示“房东声明、用户确认、证据核验、冲突、拒绝”。
7. 多表写入、发布付费和通知必须共享事务。
8. 旧房源允许不完整展示；新提交房源必须满足新版本的核心完整性规则。
9. 迁移必须遵循“先加可空字段/新表，再回填和双读写，最后收紧约束”的顺序。
10. 真实 MySQL 与测试 schema 必须由同一迁移来源生成或验证。

## 8. 待与用户商定的设计决策

现状盘点完成后，下一步已经进入新数据库表设计。按约定在这里停止实施，等待确定：

1. 数据库迁移唯一所有者；
2. 主表采用兼容旧字段的增量扩展，还是建立新版房源聚合根；
3. 家电与普通设施分表，还是统一特征表；
4. 是否在阶段 1 同时引入房间明细；
5. 是否在阶段 1 引入通用字段来源/证据表；
6. 多图表中是否同时支持视频和 VR；
7. 房源删除改为软删除，还是重新制定所有外键的物理删除规则；
8. 地区层级以真实库字符串枚举为准，还是迁移为数值枚举。

这些决策确定后才能输出最终 ER 关系、字段字典、索引、约束、回填和回滚方案。
